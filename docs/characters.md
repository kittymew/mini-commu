# 4단계 캐릭터 관리

캐릭터 생성·이름/소개/프로필 수정·선택·사용 중지·재개·삭제를 실제 DB와 연결합니다. 활성 캐릭터는 계정당 최대 6개입니다. 사용 중지 캐릭터는 선택/작성할 수 없고 활성 한도에서는 빠집니다. 다시 사용하려면 활성 자리가 있어야 합니다. 삭제는 복구할 수 없는 논리 삭제이며 ID와 과거 작성 이력은 보존합니다.

## 데이터와 동시성

- `create_character`는 로그인 계정에서 소유 관계를 만들고 이름 1~30자, 소개 300자, 본인 소유의 검증 완료 이미지인지 확인합니다. 이름은 중복 가능하고 UI에서 ID 앞 8자와 함께 구분합니다. 줄바꿈은 LF로 정규화하고 Unicode 코드 포인트 수로 길이를 계산합니다.
- 생성 요청의 UUID는 재시도 키와 캐릭터 ID로 사용합니다. 같은 계정의 같은 UUID 재요청은 중복 생성하지 않습니다. 삭제한 ID를 보내도 새 캐릭터를 만들지 않습니다.
- `update_character`, `set_character_status`는 본인 소유와 `expected_version`을 검사합니다. 운영자도 다른 사람의 캐릭터를 수정할 수 없습니다. 충돌 시 입력을 보존하고 최신 목록에서 다시 수정하도록 안내합니다.
- 계정의 회원 행을 먼저 잠가 생성·사용 재개·상태 변경을 직렬화합니다. 역할 변경/정지와도 같은 회원 행에서 충돌하므로 변경 후 자격을 확인합니다. 활성 한도, ID/생성 시각, 삭제 상태, 소유 관계는 DB 트리거로도 보호합니다.
- `list_my_characters(page_offset)`는 본인의 활성/중지 캐릭터를 50개씩 반환합니다. 소유 계정 ID나 이메일은 반환하지 않습니다. 브라우저는 페이지를 모두 읽고 정상 결과가 준비된 뒤 목록을 교체합니다.

## 기기별 선택과 접근 정리

선택 캐릭터 ID는 `mini-commu:character:<계정 UUID>` 키로 현재 브라우저에 저장합니다. 별도 기기에서는 목록은 같지만 선택은 독립적입니다. 새 캐릭터 생성 시 그 캐릭터를 선택합니다. 삭제·중지되거나 저장된 ID가 유효하지 않으면 자동으로 다른 캐릭터를 고르지 않고 선택을 요청합니다. 포커스 복귀와 표시 중 15초 간격으로 서버 목록을 확인합니다.

로그아웃·정지·계정 전환 시 목록을 즉시 숨기고 선택·캐시를 비웁니다. 완료가 늦은 이전 계정의 요청은 현재 계정과 요청 세대를 확인한 뒤 무시합니다. 프로필은 인증된 Storage 다운로드를 Blob URL로 표시하고 화면에서 사라지면 `URL.revokeObjectURL`로 폐기합니다. 영구 데이터나 localStorage에 만료 URL을 저장하지 않습니다.

## 프로필 이미지

프로필 교체에 필요한 이미지 처리부터 이번 단계에 구현했습니다. 게시글 첨부·전체 미참조 파일 정리는 [5단계](posts.md)에 추가했습니다. Supabase 유료 이미지 변환은 사용하지 않습니다.

| 제한 | 값 |
| --- | --- |
| 입력 | JPEG/PNG/WebP, 10 MiB 이하, 비애니메이션 |
| 원본 해상도 | 1,200만 화소 이하, 각 변 8,192px 이하 |
| 배포 이미지 | 긴 변 최대 2,048px, WebP 품질 82 |
| 썸네일 | 긴 변 최대 256px, WebP |
| 저장 용량 | 배포 이미지와 썸네일 합계 5 MiB 이하 |
| 요청 한도 | 계정당 1시간 20개 예약, 실패도 포함 |

`supabase/functions/profile-image/limits.mjs`를 브라우저와 서버가 함께 사용합니다. 원본은 서버에서 형식·프레임 수·크기를 검증하고 EXIF 회전을 적용한 뒤 메타데이터를 제거하여 재인코딩합니다. 원본 파일은 Storage에 남기지 않습니다. WASM 디코더에는 메모리·픽셀·프레임 제한을 적용합니다. 무료 Edge 환경의 실제 최대 CPU/메모리 안에서 처리되는지는 배포 환경에서 최종 검증해야 합니다.

1. 서버가 Auth `getUser`로 JWT를 검증합니다. 요청 본문의 사용자 ID는 받지 않습니다.
2. 사용자 JWT로 `reserve_profile_asset()`를 호출해 활성 회원과 요청 한도를 확인합니다. 자산은 `pending`이고 다운로드/캐릭터 연결이 불가능합니다.
3. 검증·변환한 파일을 서버 키로 `profiles/<새 자산 UUID>/main.webp`, `thumb.webp`에 저장합니다. `upsert:false`로 이전 경로를 덮어쓰지 않습니다.
4. 서버 전용 `finalize_profile_asset`가 회원 상태를 다시 확인하고 `ready`로 확정합니다. 브라우저는 이 함수를 호출할 수 없습니다.
5. 캐릭터 RPC가 자산 소유/상태를 검사하고 참조를 변경합니다. 이전 자산은 삭제하지 않습니다. 본인 소유 프로필 또는 정상 콘텐츠에서 참조되는 이미지에만 접근할 수 있습니다.

실패 시 이미 업로드한 새 파일은 제거를 시도하고 자산을 `rejected`로 표시합니다. 네트워크 단절로 정리가 실패하거나 업로드 후 사용자가 편집을 취소하면 미참조 자산이 남을 수 있습니다. 5단계의 전체 참조 검사 기반 정리 명령으로 처리합니다. 현재는 임의로 삭제하지 않아 과거 이미지가 손실되지 않습니다.

## 스냅샷 저장

`posts`와 `comments`의 INSERT 트리거가 실제 요청자의 활성·소유 캐릭터를 잠그고 이름/이미지/작성 시각을 서버에서 복사합니다. 같은 트랜잭션의 AFTER INSERT 트리거가 비공개 작성자 계정 관계를 저장합니다. 입력한 이름이나 이미지 ID를 그대로 신뢰하지 않습니다. 이후 캐릭터의 이름·프로필·상태가 바뀌어도 저장된 글·댓글의 스냅샷은 불변이고 참조 이미지 삭제는 FK로 차단됩니다.

5단계의 글·댓글 생성 RPC가 이 트리거를 사용합니다. 테이블 직접 INSERT 권한은 열지 않았습니다. 4단계 검증에서는 신뢰된 SQL 연결에 각 사용자 JWT 컨텍스트를 설정하고 글·댓글을 실제로 저장해 스냅샷과 소유 관계를 확인합니다. 기존의 SQL 소유자 전용 이관/테스트 데이터 입력은 JWT가 없는 신뢰된 연결에서만 허용합니다.

## 로컬 및 배포

`pnpm dev:local`과 `pnpm test:auth`는 앱 외에 `127.0.0.1:54325`에 로컬 이미지 HTTP 어댑터를 함께 실행하고 종료합니다. 동일한 처리 함수를 Node 24에서 실행하며 실제 로컬 Auth·DB·Storage에 요청합니다. 이는 아직 클라우드 Deno Edge 런타임에 배포한 결과를 의미하지 않습니다.

클라우드 진입점은 `supabase/functions/profile-image/index.ts`, 고정 의존성은 해당 폴더의 `deno.json`입니다. 함수 자체가 JWT를 검증하므로 `verify_jwt=false`로 구성했습니다. `APP_ORIGINS=https://kittymew.github.io`를 서버 비밀 설정에 넣고 허용된 origin만 CORS에 반환합니다. Supabase 서버 키는 함수 런타임에서만 사용하고 Vite에는 전달하지 않습니다. 기본 업로드 URL은 `<Supabase URL>/functions/v1/profile-image`입니다. 로컬 도구만 `VITE_PROFILE_UPLOAD_URL`을 어댑터 주소로 덮어씁니다.

참고: [Supabase WASM 이미지 처리](https://supabase.com/docs/guides/functions/examples/image-manipulation), [magick-wasm](https://github.com/dlemstra/magick-wasm).
