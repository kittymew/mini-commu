초대 가입 DB/API 검증:

- 실제 초기 초대로 가입한 인증 계정을 서버 소유자 절차로 최초 운영자 지정.
- 비로그인·이메일 미인증 계정의 코드 사용 거부와 미소진 확인.
- 만료·폐기·소진·오입력에 같은 오류 반환, 미가입 상태 유지.
- 마지막 1회 코드에 동시 가입한 두 계정 중 한 계정만 등록.
- 한 계정이 서로 다른 코드를 동시에 요청해도 총 1회만 소진. 재시도 멱등성 확인.
- 동시에 실패한 7개 요청 중 5개만 검사하고 나머지 차단. 정상 코드도 제한 기간 내에는 차단하며 15분 뒤 재시도 성공. 제한 기록 직접 삭제 거부.
- 정지 계정이 기존 JWT와 새 초대 코드로 재활성화할 수 없음.
- 활성 운영자만 초대를 발급·조회·변경하며 목록에 원문·해시가 없고 감사 기록에는 ID만 남음.

인증 E2E는 아래 7개 흐름을 데스크톱과 Pixel 7 화면 크기에서 각각 실행했습니다.

1. 가입 → 실제 Mailpit 인증 링크 → PKCE 교환 → 초대 확인 → 가입 완료 → 새로고침 → 다른 브라우저 로그인 → 로그아웃과 캐시 정리.
2. 가입 미완료 계정의 피드 차단, 잘못된 코드 오류 후 정상 코드로 가입, URL에 초대 원문 미포함.
3. 실제 복구 메일 → 비밀번호 확인 불일치 → 변경 성공 → 이전 비밀번호 실패·새 비밀번호 로그인 성공 → 사용된 링크 거부.
4. 기존 로그인 계정의 이용 정지 후 화면 차단·캐시 정리·재가입 차단.
5. 인증 메일 재발송, 별도 브라우저에서 PKCE 교환 불가 안내 후 이메일/비밀번호 로그인으로 가입 재개.
6. 회원 조회 네트워크 실패 시 보호 화면 차단과 재시도 복구.
7. 만료된 세션의 실제 Auth refresh 성공, 무효 refresh token의 로그인 복귀와 캐시 정리.

성공 응답을 모킹하지 않았습니다. 네트워크 장애 테스트에서만 요청을 중단했습니다. 브라우저 테스트 계정·초대와 DB 테스트 픽스처는 실행 후 삭제합니다. 인증 trace/스크린샷/동영상은 수집하지 않습니다.

A01/A02의 실제 가입과 동시성, A03의 DB/Storage 및 화면 차단, A04의 로그인 유지와 로컬 하위 경로 인증·복구, A22의 계정 상태 정리, A24의 로컬 검사를 확인했습니다. 아직 없는 콘텐츠와 내보내기, 다른 기기의 캐릭터·작성글 동기화까지 검증한 것은 아닙니다. 정지 시 이미지 접근 정보 정리는 현재 정리 로직과 테스트 키로 확인했고 실제 이미지 화면은 5단계에서 검증합니다.

GitHub Actions에도 실제 로컬 인증 E2E를 추가했습니다. 클라우드 Supabase 연결·외부 SMTP 발송·GitHub Pages 배포·실제 모바일 기기/Safari·무료 할당량 내 부하 검증은 이번 단계에서 수행하지 않았습니다. 별도 유료 리소스는 만들지 않았습니다.

# 4단계 검증 기록

검증일: 2026-10-20 (Asia/Seoul). 클라우드·유료 리소스 없이 로컬 PostgreSQL·Auth·Storage와 실제 이미지 처리 함수를 사용했습니다. 기존 DB를 초기화하지 않고 마이그레이션 3개를 추가했습니다.

| 항목 | 결과 |
| --- | --- |
| `pnpm db:migrate` | 캐릭터·프로필 자산·불변 조건 마이그레이션 적용 |
| `pnpm db:test` | 실제 DB/API/이미지 처리 34개 통과 |
| `pnpm db:types:check` | public 스키마와 생성 타입 일치 |
| SQL lint | public·private 스키마 오류 없음 |
| `pnpm check` | 린트·타입 검사·프로덕션 빌드 통과 |
| `PLAYWRIGHT_CHANNEL=chrome pnpm test:auth` | 데스크톱·Pixel 7 크기에서 인증/캐릭터 22개 통과 |
| 환경변수 없는 빌드 후 `PLAYWRIGHT_CHANNEL=chrome pnpm test:e2e` | 기본 화면/하위 경로 6개 통과 |

추가한 DB/API 검증은 다음 10개 흐름을 포함합니다.

1. 이름 중복, Unicode 코드 포인트 길이, 소개 LF 정규화와 서버 길이 제한.
2. 동시 생성 8건 중 6건만 성공, 생성/재개 경합에서도 활성 6개 유지, 중지/삭제 후 자리 확보, 삭제 ID 복구 금지.
3. 동일 요청 UUID 재시도 멱등성과 동시 수정 충돌.
4. 본인 소유 검사, 운영자도 타인 수정 불가, 미가입/정지/비로그인 요청 및 테이블 직접 쓰기 거부.
5. 실제 바이트 업로드 → 검증/변환 → private Storage 저장 → 본인 캐릭터 연결. 타인/미완료 자산 연결과 회원의 서버 확정 RPC 거부.
6. 글·댓글 등록 시 위조 스냅샷 덮어쓰기, 비공개 작성 계정 저장, 캐릭터 이름/이미지 변경·삭제 후 과거 스냅샷과 이미지 접근 보존. 소유자/캐릭터 ID/스냅샷 변경 및 참조 자산 삭제 거부.
7. 타인 또는 중지 캐릭터로 스냅샷 등록 거부.
8. 비인증/정지/미가입 업로드, MIME 위장, SVG, 애니메이션 PNG, 과도한 용량 거부 및 실패 자산 상태 확인.
9. 실제 EXIF 회전과 메타데이터 제거, 2,048px 본 이미지와 256px 썸네일 변환.
10. 시간당 업로드 예약 20개 한도와 서버 429 응답.

스냅샷 INSERT 검증은 신뢰된 SQL 연결에 개별 사용자 JWT 컨텍스트를 설정해 실행했습니다. 글/댓글 일반 쓰기 API와 화면은 5단계이므로 그 경로의 완성까지 의미하지 않습니다. 캐릭터/자산 권한 검사는 실제로 구분된 회원·운영자·정지·미가입 JWT와 PostgREST/Storage 요청을 사용합니다.

브라우저에는 기존 인증 7개에 캐릭터 흐름 4개를 더해 각 화면 크기에서 실행했습니다. 실제 프로필 교체와 별도 경로, 새로고침/다른 브라우저의 목록 일치와 독립적인 선택, 6개 한도, 수정 충돌 시 입력 보존, 다른 창 삭제 후 선택 해제, 잘못된 이미지 재시도, 로그아웃 시 실제 Blob URL 폐기와 다음 계정 격리를 확인했습니다. 비밀번호 복구 완료 화면을 유지하도록 Provider 마운트 문제를 수정했고, 선택/소개 입력란의 라벨을 명시적으로 연결했습니다. 개인정보가 없는 테스트 캐릭터 목록을 데스크톱과 모바일 이미지로 직접 확인했으며 가로 넘침이 없습니다. 인증 화면은 녹화하지 않았습니다.

A06과 A08의 DB 불변 조건, A04의 캐릭터 기기 간 조회, A09의 캐릭터 소유 경계, A22의 실제 선택/이미지 정리를 확인했습니다. A07은 스냅샷 저장 기반을 검증했으며 작성/수정 화면을 통한 전체 흐름은 5단계에 이어서 검증합니다. A10/A21/A23은 프로필 이미지·캐릭터 부분에 한정하며 게시글 기능까지 통과한 것으로 간주하지 않습니다.

로컬 이미지 HTTP 어댑터는 Edge 진입점과 같은 처리 함수를 Node 24에서 실행합니다. 실제 Supabase Deno 배포 번들과 WASM 포함 여부, Free CPU/메모리 한도, 외부 SMTP, GitHub Pages 배포는 미검증입니다. 유료 이미지 변환은 사용하지 않습니다. 미참조 이미지 정리는 5단계에서 전체 참조 보호와 함께 구현하며, 현재 이전 프로필은 자동 삭제하지 않습니다.
