# 운영과 초기 설정

현재 8단계 최종 검증과 조건부 Pages 배포 설정, 운영 문서까지 구현했습니다. 실제 클라우드 프로젝트·Pages 배포·운영 백업은 아직 연결하지 않았습니다.

## 최초 운영자

최초 가입자를 자동으로 운영자로 지정하지 않습니다. 첫 초대는 운영자가 없을 때에도 **신뢰할 수 있는 DB 소유자 연결**에서 발급할 수 있습니다. 브라우저·일반 API·service_role에는 bootstrap 실행 권한을 주지 않습니다.

1. Supabase SQL Editor 또는 관리용 SQL 연결에서 `select private.issue_bootstrap_invite();`를 실행합니다. 무작위 코드는 이 결과에서만 보여주고 DB에는 SHA-256 해시만 저장합니다. 원문을 URL, 소스, 로그에 남기지 않고 대상 사용자에게 전달합니다. 기본 1회용·7일이며 사용 가능한 초기 코드가 이미 있으면 중복 발급을 거부합니다.
2. 대상 계정이 이메일 인증과 해당 코드로 정상 초대 가입을 완료해야 합니다. 로컬에서는 가입 화면과 테스트 메일함을 사용합니다. 실제 서비스는 클라우드 연결과 SMTP 설정 후 같은 가입 절차를 따릅니다.
3. 관리용 SQL 연결에서 `select private.bootstrap_admin('인증과_가입을_마친_계정_UUID'::uuid);`를 실행합니다. 이메일 인증·활성 회원·초대 사용 기록을 모두 검증하고 운영 기록을 남깁니다.
4. 활성 운영자가 이미 있으면 bootstrap은 실패합니다. 이후 운영자 추가·회수는 `change_member_role`을 사용합니다. 마지막 운영자를 없애는 변경은 막습니다.

실행 예시는 `supabase/admin/bootstrap.sql`에도 주석으로 제공하며 파일을 그대로 실행해도 계정을 변경하지 않습니다. 만료·분실한 초기 코드는 DB 소유자가 해당 코드 ID를 확인해 `revoked_at`을 설정한 뒤 새로 발급합니다. 해시에서 원문을 복구하거나 회원 가입 조건을 수동으로 우회하지 않습니다.

## 무료 요금제 기준

2026-10-19 확인 기준 Free는 DB 500 MB, Storage 1 GB, 월 일반/캐시 전송량 각각 5 GB, 월 활성 사용자 50,000명, Edge Functions 월 500,000회입니다. 실제 한도는 배포 전에 [공식 요금표](https://supabase.com/pricing)에서 다시 확인합니다.

이번 단계는 PostgreSQL·Auth·RLS·비공개 Storage만 사용합니다. 유료 이미지 변환, 벡터/분석 버킷, PITR, 유료 확장 기능에 의존하지 않습니다. 로컬에서는 유료 한도가 자동으로 시뮬레이션되지 않으며 클라우드 사용량은 대시보드에서 관리해야 합니다.

- 무료 프로젝트의 비활동 일시 중지와 자동 백업 미포함을 운영 조건에 반영합니다.
- 실제 서비스의 가입·복구 메일은 외부 SMTP를 설정합니다. Supabase 기본 메일 발송은 팀 주소 대상 테스트용입니다. SMTP와 발신 도메인 비용은 공급자 조건을 별도로 확인하며, 이번 단계에서는 연결하지 않습니다.
- 프로필과 첨부 이미지는 유료 이미지 변환 API 없이 서버 검증·압축을 수행합니다. 사진·과거 프로필 보존으로 Storage가 누적되므로 사용량을 관리합니다.
- 무료 한도 초과 시 자동 유료 업그레이드를 수행하지 않습니다.

## 후속 운영 작업

이미지 저장 한도와 참조 보호를 구현했습니다. 아래 DB·Storage 백업/복원 절차를 제공하며, 외부 저장소 연결과 실제 복원 검증은 아직 수행하지 않았습니다. 회원 PDF/JSON 내보내기는 서비스 복구용 백업을 대체하지 않습니다.

## 초대 코드 관리와 가입 제한

활성 운영자로 로그인한 세션에서 `issue_invite(valid_days, use_limit)`를 호출합니다. 기본은 7일·1회입니다. 반환된 `code`는 발급 시에만 표시되며 `list_invites()`에는 ID·만료일·한도·사용량·폐기 시각만 반환됩니다(최근 100개). `update_invite(target_id, expiry, use_limit, revoke_code)`로 만료·한도 조정과 폐기가 가능합니다. 사용량보다 낮은 한도는 거절하며 폐기한 코드를 되살리지는 않습니다. `/admin`의 초대 코드 탭에서 발급·만료/한도 수정·폐기를 제공합니다. 초대 목록은 최근 100개이며 원본 코드 재조회는 제공하지 않습니다.

`redeem_invite`는 이메일 인증 후 계정당 15분에 최대 5번 검사합니다. 초대 유효성을 알 수 없게 만료·폐기·소진·오입력은 같은 오류로 안내합니다. 실패 요청도 횟수에 포함되며 일반 API로 제한 기록을 수정할 수 없습니다. 성공한 계정은 재요청해도 추가 소진하지 않으며 이용 정지 계정은 새 코드로 복귀할 수 없습니다.

로그인·메일 전송에는 Supabase Auth 자체 요청 제한도 적용합니다. 저장소의 `sign_in_sign_ups=200`은 여러 로컬/CI 계정이 한 루프백 IP를 쓰기 위한 테스트 설정입니다. 클라우드는 기본 제한을 유지하고, 공개 운영 시 Auth CAPTCHA를 사용할 경우 공급자 연결과 화면 설정을 함께 검증합니다. 클라이언트의 버튼 비활성화만으로 요청 제한을 대체하지 않습니다.

## 프로필 운영

활성 캐릭터는 계정당 6개이며 중지·삭제로 자리가 생깁니다. 재개 시에도 같은 한도를 검사합니다. 프로필 업로드는 계정당 시간당 20개 예약으로 제한하고 실패도 횟수에 포함합니다. 교체 전 이미지는 과거 글과 댓글에서 참조할 수 있으므로 임의로 Storage 경로를 지우지 않습니다. 미참조 자산은 아래 절차로 정리합니다. [세부 동작](characters.md)을 참고하세요.


## 미참조 이미지 정리

운영 시 **하루 1회** 실행을 권장합니다. 24시간보다 오래되고 어떤 현재/과거 콘텐츠에도 참조되지 않는 자산만 대상입니다. 로컬 미리보기와 실제 실행은 다음과 같습니다.

```sh
pnpm assets:cleanup --local
pnpm assets:cleanup --local --apply
```

클라우드는 신뢰된 서버/운영 작업에서만 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 주입하고 `pnpm assets:cleanup`으로 먼저 확인한 뒤 `--apply`를 붙입니다. 이 비밀 키는 Vite 환경변수나 공개 저장소에 넣지 않습니다. 명령은 기본적으로 미리보기이며 100개 단위, 실행당 최대 1,000개를 정리합니다. 실패하면 종료 코드가 실패로 끝나고 다음 실행에서 `deleting` 자산부터 다시 검사할 수 있습니다. 처음의 100개 미리보기는 전체 개수가 아닐 수 있습니다.

외부 스케줄러/클라우드 비밀값은 아직 연결하지 않았으므로 **정기 정리가 자동 실행 중인 상태는 아닙니다**. 배포 시 하루 1회 작업과 실패 알림을 설정하고 실행 로그를 확인해야 합니다. 중복 실행을 피하고, 삭제/숨김 글과 옛 프로필의 참조는 임의로 지우지 않습니다. 24시간 넘게 방치한 초안의 이미지는 다시 올려야 할 수 있습니다. 실패한 글 저장·취소된 편집의 미참조 자산도 이 유예 규칙을 적용합니다. 세부 잠금과 보존 범위는 [게시글 안내](posts.md)에 정리했습니다.

## 운영 화면과 개인정보 경계

회원 권한과 정지, 공지/고정, 글·댓글 숨김/삭제에는 사유를 남깁니다. 숨김 해제만 복구 가능하며 삭제를 되돌리는 UI/API는 없습니다. 운영자도 일반 상세·검색에서 숨긴 본문을 읽거나 익명 투표 참여자를 조회할 수 없습니다. 기명 투표 스냅샷 이미지는 과거 참조로 보존합니다. 관리 화면의 회원 이메일과 조치 기록은 일반 회원 내보내기에 포함하지 않습니다. 자세한 흐름과 조회 범위는 [6단계 안내](community.md)를 따릅니다.

## DB·Storage 백업과 복원

**현재 상태:** 아래는 운영 절차이며 실제 운영 백업·복원은 실행하지 않았습니다. 클라우드 DB, 외부 백업 저장소, 자동 스케줄과 실패 알림도 연결하지 않았습니다. 로컬 테스트 데이터 정리는 백업/복원 검증이 아닙니다. 유료 PITR나 자동 백업 상품을 활성화하지 않았습니다.

회원 내보내기는 계정·초대·비공개 소유 관계·운영 기록을 제외하므로 복구에 사용할 수 없습니다. 운영 백업에는 민감한 Auth/계정 정보가 포함될 수 있으므로 암호화하고 운영 담당자만 접근하는 저장소에 보관합니다. 공개 GitHub 저장소와 프런트엔드에는 올리지 않습니다.

### 백업 절차

1. 신뢰된 관리 환경에서 시작 시각·앱 커밋·마이그레이션 버전·DB/CLI 버전을 기록합니다. 일관된 DB와 파일 쌍을 만들기 위해 글/이미지 쓰기와 미참조 자산 정리를 중단하고 진행 중 작업이 끝난 뒤 시작합니다.
2. [Supabase 공식 백업/복원 절차](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)에 따라 관리용 DB 연결로 역할, 스키마, 데이터 덤프를 각각 생성합니다. `public`, `private`, Auth 데이터와 마이그레이션 이력을 포함했는지 확인합니다. 관리 스키마의 사용자 정의 트리거/RLS는 덤프에서 빠질 수 있으므로 저장소 마이그레이션과 실제 설정을 함께 보관합니다. 연결 비밀번호를 명령 로그에 출력하지 않습니다.
3. DB와 별도로 비공개 `community` 버킷의 모든 객체를 **페이지 끝까지** 열거해 다운로드합니다. 원래 버킷·객체 경로, 바이트 수, SHA-256, 콘텐츠 유형을 manifest에 기록합니다. 현재 프로필뿐 아니라 과거 글·댓글·기명 투표의 스냅샷 파일, 썸네일과 미완료 파일도 포함합니다. [DB 백업에는 Storage 파일 바이트가 들어가지 않습니다](https://supabase.com/docs/guides/platform/backups).
4. Auth redirect/SMTP 설정, 버킷 비공개 설정과 제한, Edge 함수 버전, 비밀값 복구 경로도 별도로 기록합니다. 실제 비밀은 암호화된 비밀 보관소에 저장합니다. DB 덤프와 파일 manifest의 체크섬/건수를 확인해 같은 백업 ID로 묶은 뒤 암호화된 외부 목적지에 복사하고 읽기 검증합니다. 완료 여부를 기록한 다음 쓰기와 정리를 재개합니다.

초기 운영 계획은 하루 1회와 마이그레이션 직전 백업, 일간 7개·주간 4개 보존입니다. 보관 비용·무료 용량을 확인하고 실제 목적지와 담당자를 정한 후 자동화합니다. 새 백업이 검증되기 전에 마지막 정상 백업을 삭제하지 않습니다.

### 격리 환경 복원 절차

1. 운영 DB를 덮어쓰지 않는 별도 호환 환경을 준비하고 외부 메일 발송·사용자 접근·정리 작업을 차단합니다. 백업 암호 해제 후 모든 파일의 체크섬을 확인합니다.
2. 공식 절차의 역할 → 스키마 → 데이터 순서로 오류 시 중단되는 관리 연결에서 복원합니다. 필요한 확장과 Auth/Storage 관리 스키마 버전을 먼저 맞춥니다. 복원한 마이그레이션 이력과 앱 커밋을 비교하고 누락된 사용자 정의 정책/트리거만 적용합니다. 기존 데이터를 초기화하는 `db:reset`은 운영 복원에 사용하지 않습니다.
3. 비공개 버킷 설정을 복구하고 Storage API/이관 도구로 실제 파일을 원래 경로에 업로드합니다. DB의 Storage 메타데이터만 복원해 파일이 복구됐다고 판단하지 않습니다. 경로 충돌은 이 복원 대상에서만 명시적으로 처리하고 manifest의 객체 수·바이트·해시를 대조합니다.
4. `public.assets`가 가리키는 본 파일/썸네일, 캐릭터와 글/댓글/투표 스냅샷 참조를 검사합니다. 별도 검증 계정으로 로그인·권한·숨김 콘텐츠 차단·이미지 다운로드·투표·회원 내보내기를 확인합니다. 비로그인/미가입/정지 사용자의 파일 접근도 차단돼야 합니다.
5. 복구 시간, 누락 건수, 검사 결과를 기록합니다. 외부 SMTP와 redirect, Edge 비밀을 대상 환경에 맞게 복구한 후 승인된 전환 시점에만 사용자 트래픽을 연결합니다. 격리 복원 시험을 통과하기 전까지는 백업의 복구 가능성을 검증했다고 보고하지 않습니다.


## 공개 전 인계와 정기 점검

공개 전에는 [배포 절차](deployment.md)의 백엔드 → 이미지 함수 → Auth/SMTP → Pages 순서를 따르고 [인수표](acceptance.md)의 외부 항목을 실제 환경에서 기록합니다. 최초 운영자와 복구 담당자, 백업 위치·암호 복구 경로, 정리 작업과 실패 알림 담당자를 지정합니다. 현재 이 외부 연결들은 미설정입니다.

운영 중에는 Free DB/Storage/전송량·함수 사용량, 인증 메일 실패, 이미지 처리 실패와 미참조 정리 결과를 점검합니다. 사용량이 한도에 가까우면 이미지 크기/내보내기 분할을 줄이고 원인을 확인하며 자동 업그레이드하지 않습니다. 로그에 JWT·비밀번호·초대 원문·회원 이메일·DB 연결문자열을 추가하지 않습니다.

권한 사고 시 활성 운영자로 대상 계정을 정지하고 조치 사유를 기록합니다. 서버 정책은 후속 요청을 차단하며 화면은 상태 갱신 때 비워집니다. 이미 내려받은 파일은 회수할 수 없습니다. 서비스 키 유출은 대시보드에서 키를 교체하고 관련 함수 비밀을 갱신합니다. 프런트엔드 문제, DB 변경, 파일 손상은 복구 경로가 다르므로 각 배포 커밋과 백업 ID를 확인합니다.

백업 작업 성공 여부는 외부 목적지의 체크섬 대조로 확인하고 격리 환경 복원 시험을 정기적으로 수행합니다. 소스 커밋이나 회원 JSON/ZIP만 보관한 것을 운영 백업 완료로 기록하지 않습니다.
